# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Claude Code Trade Analyst Agent — a deterministic Rust analytics engine for trading journal CSVs, paired with an AI coaching layer (you). The binary is `trade-analyzer`, the library crate is `trade_analyst`.

## Commands

```bash
cargo build                     # debug build
cargo build --release           # optimized native binary
cargo test                      # all tests (unit + tests/integration.rs)
cargo test parser               # tests of one module
cargo test full_pipeline        # single test by name
cargo clippy                    # lints

# Run the CLI
cargo run -- analyze <csv>      # full analysis -> vault + exchange JSON + history
cargo run -- analyze <csv> --dry-run --json   # compute only, print JSON
cargo run -- stats <csv>        # terminal stats, no writes
cargo run -- export-json <csv> [-o file]
cargo run -- inspect <csv>      # structured sample JSON for the AI mapping workflow
cargo run -- dashboard          # regenerate vault Dashboard.md
cargo run -- compare            # deltas between two latest analyses (JSON)
```

CSV commands accept `--mapping <file-or-profile-name>` (bare names resolve to `profiles/<name>.toml`, the shared per-broker library) and auto-discover `<csv>.mapping.toml` next to the CSV. Mapping files overlay `[csv]` from config.toml; `[mapping]` values are exact header names or `col:N` for duplicates.

Fixtures: `tests/fixtures/journal_trades.csv` (journal-style, every canonical field) and `tests/fixtures/sample_trades.csv` (real MT-style broker export: datetime Open/Close, duplicate Price headers). Config resolution: `--config <path>` → `./config.toml` → built-in defaults (see `config.example.toml`). Local `config.toml`, `TradingVault/` (except `.obsidian/`), `scripts/bin/` and non-fixture CSVs are gitignored. When cleaning the vault, never delete `TradingVault/.obsidian/` — it holds the user's Obsidian plugin setup.

**Engine binary resolution (skills use this order):** `scripts/bin/trade-analyzer` (downloaded release; `.exe` on Windows) → `target/release/trade-analyzer` → fetch via `scripts/update.sh` / `scripts/update.ps1` → last resort `cargo build --release`. CI (`.github/workflows/build.yml`) gates on `cargo fmt --check`, `clippy -D warnings` and tests, builds per-OS assets (`trading-analyst-agent-mac` universal / `-windows.exe` / `-linux`), and attaches them to a GitHub Release on `v*` tags.

## The one architectural rule

**Rust calculates, AI interprets — never the reverse.**

- Every number (statistics, scores, behavioral flags, history deltas) is computed deterministically in Rust. Never make the AI layer compute, estimate or "fix" a statistic, and never add an LLM call to the Rust engine.
- The two layers communicate exclusively through the **exchange JSON** (`src/ai/mod.rs`). The AI never receives raw CSV data.
- **All chart definitions are generated by Rust** (`src/charts/mod.rs` → Obsidian Charts ```chart blocks). The AI never writes or edits chart syntax — it only interprets what the charts show.

### The exchange JSON contract

`AiExchange` in `src/ai/mod.rs` defines the fixed schema: 15 top-level keys (`metadata` … `summary`, `time_series`), snake_case, no dynamic key names, `Option`/`null` for anything the input can't support. **Key order is part of the contract** — serde_json is built with `preserve_order` and struct field order defines JSON key order; tests assert it (`analyzer::tests::exchange_has_all_contract_keys`, `tests/integration.rs`). New keys are appended at the end (that's why `time_series` sits after `summary`).

Changing the schema: additive changes only, keep backwards compatibility, bump `SCHEMA_VERSION` in `src/lib.rs` (minor for additions, major for breaks). The behavioral flag names in `behavior::FLAG_NAMES` and session labels (`asia`, `london`, `overlap`, `new_york`, `other`) are also contract-stable strings.

## Pipeline & module map

```
parser (CSV -> Vec<Trade>) -> statistics/behavior/scoring -> analyzer (build_exchange)
    -> ai::AiExchange -> charts (chart specs) -> reports (visual dashboard Markdown)
                       + obsidian (vault + historical Dashboard.md) + history (snapshots)
```

- `shared` — `Trade` (only date/symbol/pnl required; everything else `Option`), `Direction`, `Session`, math helpers. All analytics degrade gracefully on missing optional fields — detectors return `data_available: false`, score components fall back to a neutral 0.5.
- `parser` — auto-detects delimiter, encoding, date format (majority vote over samples; `prefer_day_first` resolves ambiguity), decimal separator. Mapping is **content-aware**: header aliases (`Field::aliases`) only propose, sampled values must confirm (`content_compatible` — majority for alias matches, 4/5 for the name-less date rescue). This is what lets MT-style exports (datetime "Open"/"Close", duplicate "Price" columns) parse with zero config. Explicit mapping (config or mapping file, `col:N` for duplicate headers) is trusted blindly. Malformed rows are skipped and reported as warnings, never a hard failure. `inspect_csv` emits the structured sample the AI mapping workflow consumes.
- `statistics` — pure functions, trades must be sorted via `shared::sort_chronologically` first (analyzer does this). All money rounded with `round2`, ratios `round4`, for stable JSON. `time_series()` produces the per-trade/per-day chart datasets (equity, drawdown, rolling RR, streaks), stride-sampled to `MAX_TIME_SERIES_POINTS` for huge journals.
- `charts` — the reusable chart component engine: `ChartSpec` (line/bar/horizontal-bar builders) renders deterministic Obsidian Charts YAML blocks; `snapshot_charts()` builds the historical development charts shared by reports and Dashboard.md; `comparison_bar()` builds current-vs-average/best/worst bars. New visualizations = new `ChartSpec` builders consuming exchange data; never touch existing charts.
- `behavior` — 10 rule-based detectors, each always emitted with `detected`/`severity`/`confidence`/`data_available`/`metrics`. Thresholds come from `[behavior]` config. Metrics keys are fixed per flag. No prose output.
- `scoring` — 0–100 scores built from weighted 0–1 components; weights from `[scores.*]` config, normalized in `build_score`. Each component carries a terse `formula` id so the AI can explain it.
- `history` — snapshots in `<vault>/Assets/history.json`, rolling averages over the last 10, deltas vs. previous. `analyze` appends; `export-json` compares but never appends.
- `reports` — chart-first visual dashboards, fixed top-level order (Trading Period → Executive Summary → Performance → Risk → Behavior → Pair/Session/Strategy Performance → Historical Comparison → AI Coaching → Action Plan), asserted by tests. KPI tables up top, then Rust-generated charts, each group followed by a concise `<!-- ai:begin:NAME -->…<!-- ai:end:NAME -->` block. Development/history charts only render from the second analysis onward.
- `obsidian` — vault layout + `update_dashboard(&HistoryFile)`: Dashboard.md is a historical analytics dashboard (metric/score trends over all snapshots) plus links to every analysis.
- `cli` — clap subcommands; diagnostics to stderr, results to stdout (`compare`/`export-json` print pure JSON to stdout). `analyze` appends to history **before** rebuilding the dashboard so the newest analysis is included.

## Full analysis workflow ("Analyze my trades" + attached/named CSV)

Automated by the `analyze` skill (`.claude/skills/analyze/SKILL.md`): resolve binary → locate CSV → `analyze --dry-run` (detour into the csv-mapping workflow when parsing isn't clean) → `analyze` into the vault → run the coach workflow → short KPI + takeaway summary. This is the community entry point; prefer it over ad-hoc command sequences.

## AI CSV-mapping workflow (when a CSV fails to parse)

The engine never calls an LLM; instead the AI authors a **mapping file** the engine consumes. The exact repeatable procedure lives in the `csv-mapping` skill (`.claude/skills/csv-mapping/SKILL.md`) — use it whenever `analyze` fails with a missing-column error, maps columns wrongly, or skips many rows. Summary: check `profiles/` for an existing broker profile → `inspect <csv>` (read only its JSON, never the raw CSV) → decide mapping by content → save to `profiles/<platform>.toml` for named broker formats or `<csv>.mapping.toml` for one-offs → verify with `analyze --dry-run` (0 skipped rows) → `analyze`. Never bend engine code to fit one CSV format.

## AI coaching protocol (when asked to "coach" an analysis)

Automated by the `coach` skill (`.claude/skills/coach/SKILL.md`): one parallel `trading-coach` agent (`.claude/agents/trading-coach.md`) per `ai:begin` section, results applied between the markers, then verified (marker counts, no leftover `> _` placeholders, numbers exist in the JSON). The rules below are the contract those agents follow.

1. Read the newest exchange JSON from `<vault>/Assets/exchange/` (vault path from `config.toml`, default `./TradingVault`). Do not read the CSV.
2. Edit the matching report in `<vault>/Analyses/<stamp>.md`, replacing the content **between** each `<!-- ai:begin:NAME -->`/`<!-- ai:end:NAME -->` pair (keep the markers, keep the `> [!quote] Coach` callout style). Blocks: `executive_summary`, `performance`, `risk`, `behavior`, `pairs`, `sessions`, `strategies`, `historical`, `coaching`, `action_plan`.
3. **Be concise** — each block is a short interpretation of the charts directly above it (2-3 sentences; `coaching` max 5 bullets, `action_plan` max 3 actions). No essays.
4. Every claim must cite a number that exists in the JSON — never invent, recalculate or extrapolate statistics, and never write or edit ```chart blocks, tables or deterministic text. Scores are explained from `scores.*.components`, behaviors from `behavioral_flags[].metrics`, development from `historical_comparison` (`series`, `deltas`, `rolling_averages`), curves from `time_series`.
5. **Coach on trends, not isolated stats** — relate findings to historical development whenever `historical_comparison.previous_analyses > 0` ("your discipline score has risen three analyses in a row"), and skip history-dependent blocks on a first analysis.
6. Ignore flags with `data_available: false`; low `confidence` values deserve hedged language.
7. Never change the deterministic sections, the section order, or the report filename.

## Conventions

- Rust 2021, no `unsafe`. Errors via `anyhow` with `.context()`; parse-level data errors become warnings + skipped rows instead of failures.
- No new runtime dependencies without strong reason — the product ships as self-contained native binaries.
- Determinism is a feature: identical input + config must produce identical JSON (timestamps in `metadata`/filenames excepted). Anything random or time-dependent inside analytics is a bug.
- New analytics: compute in the appropriate module, add the field to `AiExchange` (additive, appended), render it in `reports`, and cover it with a unit test; behavioral detectors also need a no-false-positive case (see `behavior::tests::no_false_positive_on_clean_journal`).
- New charts: build the dataset in `statistics`/`history` (never in `reports`), add a `ChartSpec` builder or reuse one from `charts`, insert it in the matching report section, and assert the heading + a data row in a test. Charts with fewer than 2 points should be skipped with an italic note, not rendered.
